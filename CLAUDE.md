# CLAUDE.md

Инструкции для Claude по работе над проектом **AlpRoutes** — каталог альпинистских маршрутов (Android + веб).

> Переименуйте проект под своё рабочее название и правьте этот файл по мере развития. Он читается в начале каждой сессии, поэтому держите его актуальным и не раздувайте: всё, что устарело, лучше удалять, а не помечать «устарело».

---

## 1. Что это за продукт

Каталог альпинистских маршрутов с привязкой к карте. Пользователь находит маршрут по району или по карте, читает описание, смотрит фотографии с прорисованной ниткой, скачивает GPX-трек и архивное PDF-описание, после восхождения добавляет свою запись и комментарии.

**Два клиента, один backend.** Android-приложение и веб-интерфейс — равноправные клиенты единого API. Любая логика, которая может жить на сервере, живёт на сервере.

**Целевой пользователь** — альпинист в горах, часто без связи, часто в перчатках, часто на морозе. Из этого следуют три жёстких требования, которые перевешивают эстетику:

1. Офлайн-режим — не фича, а базовое условие работы.
2. Крупные элементы управления, высокий контраст, читаемость при ярком солнце.
3. Экономия батареи: никакого лишнего фонового GPS и сетевой активности.

## 2. Стек

| Слой | Технология |
|---|---|
| БД | PostgreSQL 16 + PostGIS 3 |
| Файлы | S3-совместимое хранилище (MinIO локально) |
| Backend | Kotlin + Spring Boot, REST + OpenAPI |
| Auth | JWT (access + refresh), OAuth через Google/Apple |
| Android | Kotlin, Jetpack Compose, MVI, Room, Ktor Client, WorkManager, Coil |
| Карта (Android) | MapLibre GL Native |
| Web | Next.js (App Router), TypeScript, MapLibre GL JS, pdf.js |
| Тайлы | OpenTopoMap / собственный тайл-сервер на OSM + DEM |
| Инфра | Docker Compose локально, миграции через Flyway |

**Не предлагать Google Maps SDK.** Для горной местности он непригоден: нет рельефа, нет офлайн-тайлов нужного качества, лицензия ограничивает кэширование. Карта везде — MapLibre, стиль общий для Android и веба.

## 3. Структура репозитория

```
/backend        Spring Boot API
/android        Android-приложение
/web            Next.js
/web-prototype  прототип UI (React + Vite + Leaflet, демо-данные, GitHub Pages) — референс дизайна, не основа /web
/shared         OpenAPI-спецификация, общие схемы, стили карты
/infra          docker-compose, миграции (`/infra/db/migration`), тесты схемы (`/infra/db/tests`)
```

Монорепозиторий. Контракт API живёт в `/shared/openapi.yaml` и является источником истины: клиентские модели генерируются из него, а не пишутся руками.

## 4. Модель данных

Основные сущности:

- **Area** — район/массив/вершина, иерархия через `parent_id` (Кавказ → Безенги → Дых-Тау)
- **Route** — маршрут: название, `area_id`, категория сложности, тип, перепад, протяжённость, сезонность, первопроходцы, год первопрохождения, геометрия — произвольный набор объектов `RouteFeature` (см. ниже)
- **Track** — GPX/KML: ссылка на файл в S3 + геометрия в БД, автор, дата
- **Photo** — фото: URL, EXIF-координаты, тип (`overview` / `topo` / `detail`), для `topo` — векторная прорисовка нитки в JSON
- **Document** — архивный PDF: URL, тип источника, год, правовой статус
- **Ascent** — запись о восхождении: пользователь, маршрут, дата, состав группы, условия, ходовое время
- **Comment** — комментарий к маршруту или к `Ascent`
- **User**, **RouteRevision**, **ModerationFlag**

### Правила работы с данными

- Геометрия всегда в **EPSG:4326**. Расчёты расстояний — через `geography`, не `geometry`.
- Геозапросы — только средствами PostGIS (`ST_DWithin`, `ST_Intersects`, `ST_MakeEnvelope`). Никакой фильтрации по bbox в коде приложения.
- Медиафайлы **никогда** не хранятся в БД и не проходят через backend при загрузке. Только pre-signed URL напрямую в S3.
- Описания маршрутов версионируются (`RouteRevision`). Правка не затирает предыдущую версию.
- Категория сложности хранится не строкой, а структурой: `{system, value}`. Системы: `RU`, `IFAS` (фр. альпийская F…ABO), `UIAA`, `FR_FREE` (фр. скальная), `YDS`, `AID` (ИТО), `WI` (лёд). Значения — только из справочника `grade_values` (в `RU` буквы кириллические). У маршрута несколько градаций, не больше одной на систему. Конвертация между системами приблизительна — **никогда не конвертировать молча**, всегда показывать исходную систему.
- Ревизия маршрута — полный снимок всех атрибутов (район, категории, геометрия), append-only. В `routes` только id, slug и статус; опубликована одна ревизия с `is_current`. Откат — новая ревизия-копия. Прорисовки нитки версионируются так же.
- Геометрия маршрута — любой набор (в том числе пустой) точек `start`/`summit`/`bivouac`/`descent_start` и линий `route_line`/`approach`/`descent`. Нитка не обязательна: можно ограничиться началом и вершиной. Всё только **2D**, высоты — из DEM или GPX. Линию можно импортировать из GPX-трека маршрута (геометрия копируется в ревизию). Геопоиск — по кэшу `route_geo` текущей ревизии.
- Тексты каталога — `LocalizedText` (jsonb `{"ru": ..., "en": ...}`), API отдаёт все переводы. Пользовательский контент не переводится, несёт `language`.
- Пользовательский контент создаётся с `id` от клиента (UUID) — повтор запроса идемпотентен. Удаление мягкое (`deleted_at`), чтобы доходило до офлайн-копий.

## 5. Архитектурные правила

### Backend
- Слои: `controller` → `service` → `repository`. Контроллер не содержит бизнес-логики, репозиторий не знает о DTO.
- Любой эндпоинт, возвращающий список, — с пагинацией. Без исключений.
- Миграции только через Flyway, файлы неизменяемы после мержа.
- Доступ к БД — Spring JDBC и SQL-запросы, без JPA: append-only ревизии, jsonb и PostGIS-функции проще и прозрачнее в SQL. Геометрия идёт через `ST_AsGeoJSON` / `ST_GeomFromGeoJSON`, nullable-параметры — через `CAST(:p AS type)` и типизированный `params { }`.
- DTO backend пишутся вручную строго по `/shared/openapi.yaml` (генератор для сервера не используется). Соответствие контракту проверяют интеграционные тесты. Клиентские модели генерируются.
- Интеграционные тесты — Testcontainers с образом `postgis/postgis`, не H2 и не голый Postgres.

### Android
- Clean Architecture: `data` / `domain` / `ui`. `domain` не зависит ни от Android SDK, ни от сети.
- **Room — единственный источник истины для UI.** Сеть пишет в Room, UI читает из Room. Экран никогда не подписывается на результат сетевого запроса напрямую.
- Любая запись пользователя (комментарий, запись о восхождении, загрузка фото) сначала сохраняется локально со статусом `pending`, затем синхронизируется через WorkManager. Отсутствие сети не должно приводить к потере данных или к ошибке на экране.
- Состояние экрана — один immutable data class. События — sealed interface.
- Никаких `!!`, никакого `GlobalScope`.

### Web
- Страницы маршрутов и районов — серверный рендеринг ради индексации поисковиками. Это значимый канал притока пользователей, не жертвовать им ради удобства разработки.

## 6. Порядок разработки

Текущий этап отмечайте здесь же.

Весь функционал сначала делается в вебе: через него на начальном этапе наполняется база. Android подключается, когда веб-версия готова. Контракт API и схема с самого начала учитывают офлайн-работу Android (id от клиента, мягкое удаление), это не откладывается.

- [x] **Шаг 1** — схема БД и OpenAPI-контракт
- [ ] **Шаг 2** — backend MVP: CRUD маршрутов, auth, загрузка в S3, геопоиск по bbox
- [ ] **Шаг 3** — веб: каталог, карта, SSR-страницы районов и маршрутов, редактирование маршрутов (включая геометрию на карте), модерация
- [ ] **Шаг 4** — веб: пользовательский контент — фото и редактор нитки, GPX (с импортом линий в маршрут), восхождения, комментарии, жалобы
- [ ] **Шаг 5** — веб: фильтры, поиск, профили, экспорт GPX
- [ ] **Шаг 6** — Android MVP, только чтение
- [ ] **Шаг 7** — Android: пользовательский контент, офлайн-режим (скачивание района целиком), deep links

## 7. Ключевые фичи, которые легко недооценить

**Прорисовка нитки по фото.** Это то, ради чего альпинисты открывают каталог. Нужен полноценный редактор: загрузка фото, рисование линии с точками страховочных станций, подписи участков, сохранение в виде векторных координат относительно размеров изображения (не в пикселях исходника). Отрисовка поверх фото на обоих клиентах.

**Профиль высот из GPX.** Барометрические и GPS-высоты расходятся сильно. Сглаживать и при возможности сверять с DEM, а не строить график по сырым данным.

**Офлайн-пакет района.** Тайлы карты + описания + фото + GPX одним скачиванием, с показом размера до начала загрузки и возможностью удалить.

**Модерация.** Открытый каталог без модерации зарастает мусором за месяцы. Закладывать флаги, очередь на проверку и откат правок с самого начала, а не после запуска.

## 8. Правовое и этическое

- Архивные PDF-описания из классификаторов маршрутов, как правило, защищены авторским правом. **Не публиковать без выясненного правового статуса.** У каждого `Document` обязательно поле с источником и статусом прав.
- На каждой карточке маршрута — дисклеймер: описание не гарантирует безопасность, условия меняются, ответственность на восходителе.
- Не генерировать и не додумывать фактические данные о маршрутах: категории, перепады, координаты, имена первопроходцев. Если данных нет — оставлять пустым и помечать. Выдуманная категория сложности в альпинистском каталоге — это вопрос жизни людей, а не косметический дефект.

## 9. Как Claude должен работать над задачами

- Перед изменением кода прочитать соответствующие существующие файлы. Не переписывать модуль целиком, если задача — локальная правка.
- Если задача затрагивает контракт API — сначала обновить `/shared/openapi.yaml`, потом клиентов.
- Изменения схемы БД — только новой миграцией Flyway.
- Если требование неоднозначно (особенно касающееся градаций, геометрии или офлайна) — задать уточняющий вопрос, а не выбрать вариант молча.
- Говорить прямо, если предложенное решение выглядит проблемным. Указывать на ошибки, риски производительности и архитектурные тупики, даже когда об этом не спрашивали.
- Не добавлять новые зависимости без объяснения, что именно они решают и почему не хватает уже имеющихся.
- Код и комментарии в коде — на английском. Общение, документация и пользовательские тексты — на русском.

## 10. Команды

```bash
# Инфраструктура (Postgres+PostGIS, MinIO)
docker compose -f infra/docker-compose.yml up -d

# Миграции без backend и тесты схемы (подробнее — infra/db/README.md)
docker compose -f infra/docker-compose.yml run --rm flyway migrate
docker compose -f infra/docker-compose.yml exec db psql -U alproutes -d alproutes -v ON_ERROR_STOP=1 -f /db-tests/constraints_test.sql
docker compose -f infra/docker-compose.yml exec db psql -U alproutes -d alproutes -v ON_ERROR_STOP=1 -f /db-tests/postgis_test.sql

# Backend (dev-профиль: вход через POST /auth/dev-login, без OAuth)
cd backend && ./gradlew bootRun --args='--spring.profiles.active=dev'
cd backend && ./gradlew test          # нужен Docker (Testcontainers + PostGIS)

# Web
cd web && npm run dev
cd web && npm run build

# Android
cd android && ./gradlew assembleDebug
cd android && ./gradlew testDebugUnitTest
```

> Актуализируйте этот раздел, когда команды изменятся — Claude полагается на него и не должен угадывать способ сборки.
